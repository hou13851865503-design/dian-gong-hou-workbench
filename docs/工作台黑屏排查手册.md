# 工作台「重启后双击黑屏」排查手册

> 适用症状：**开机/重启后的第一次双击桌面快捷方式，进不去，直接一片黑**；用过一段时间后再双击往往正常。
> 本文按「启动配置 → 依赖服务/环境变量 → 缓存/状态文件 → 显卡/显示」四条线给结论，最后给验证方法。

---

## 一、先看清"黑屏"是哪一种

黑屏至少有四种，处理方式完全不同。启动器现在的日志会把它们区分开（`portal_launcher.log`）：

| 现象 | 日志特征 | 真实含义 |
|---|---|---|
| 一片黑、没有任何窗口 | 只有 `启动器开始`，之后没有 `门户已就绪` | 服务没起来 / 脚本没跑起来 |
| 有窗口、标题是 `127.0.0.1_/` | `页面加载=False 标题=127.0.0.1_/` | **页面没加载**（服务或代理没通），不是渲染问题 |
| 有窗口、标题是 `电工猴的此思妙想工作台`、但屏幕是黑的 | `页面加载=True` + `像素判定：BLACK` | 真的渲染黑了（合成/驱动） |
| 有窗口、正常内容，但你没看到 | `置前结果：FOCUSED 0` | **窗口被别的窗口盖住了**（开机自启程序抢前台） |

最后一种是"重启后必现"最主要的嫌疑：开机后 OneDrive、Steam、Nexus、Rainmeter、WorkBuddy、桌宠（Electron）、Edge 后台（`--no-startup-window`）会在十几秒内陆续启动并抢焦点/覆盖。

## 二、根因分析（四条线）

### 1. 启动配置

| 问题 | 证据 | 后果 | 处理 |
|---|---|---|---|
| 黑屏重试只等 1.2 秒就重开 Chrome | 旧版 `Close-PortalChrome; Start-Sleep -Milliseconds 1200` | Chrome 在退出过程中的 1~2 秒内会**把新启动的进程"吞掉"**（新进程 ExitCode=0、无窗口），看起来就是"点了没反应" | 现在等所有 chrome 进程真正清零 + 600ms，并识别"启动即退出"后退避重试（最多 3 次） |
| 双击两次 → 两个启动器互相杀窗口 | 无互斥 | 第二个实例的 `Close-AppChrome` 会把第一个刚打开的窗口关掉 | 加单实例互斥 `Local\DianGongHouWorkbenchLauncher` |
| 冷启动时"窗口先出来、页面后加载"被当成成功 | 旧版 `Wait-AppWindow` 只要拿到窗口就 return true | 页面没加载也报成功，用户看到的是一张空白/黑窗口 | 改成等窗口标题变成工作台标题，才认为页面真加载 |
| 服务端口探测对 21 个端口每个盲等 1.5 秒 | 日志 `[+32.3s] 已拉起门户服务`，启动前先空转 32 秒 | 双击后长时间没反应，用户以为失败又双击 | 先只看 8770（一次请求），被占用才往后扫；启动总耗时 93s → 约 10s |

### 2. 依赖服务 / 环境变量

| 问题 | 证据 | 处理 |
|---|---|---|
| 只按"端口返回 200"认服务 | 8787 上可能跑着 New API | 必须校验 `/api/health` 里的 `portal=workbench`（已在前几轮修复，保留） |
| 开机时 FlClash 可能已开系统代理、但内核还没起来 | 本机 `ProxyEnable=0`、`ProxyOverride` 含 `127.*`，当前不是阻塞点；但这是历史高频故障 | 给 Chrome 加 `--no-proxy-server`：本机页面永远不走代理 |
| 环境里同时存在 `http_proxy` 和 `HTTP_PROXY` 时，PowerShell 构造子进程环境块会抛"已添加了具有相同键的项" | 日志 `pixel check failed: 已添加项。字典中的关键字:"http_proxy"`；同一会话里 `Start-Process -RedirectStandardError` 也复现过 | 启动器不再用 `-RedirectStandardOutput/Error`，子进程结果一律写文件回传 |
| 黑屏检测失败时被当成成功 | 日志 `pixel check failed...` 紧接着 `pixel=skipped` → 判定"窗口就绪" | 改为三态：`OK / BLACK / 无法判定`；"无法判定"不杀窗口、如实记日志 |

### 3. 缓存 / 状态文件

| 问题 | 证据 | 处理 |
|---|---|---|
| 像素检测用固定临时文件 `%TEMP%\wb_pixel_check.txt` | 该文件至今存在，内容 `OK 5% 2000x1536`（19:01 写入） | 每次用 `[guid]` 唯一文件名；删不掉就直接放弃本次结果，绝不读旧值 |
| Chrome 专用 profile 可能残留 `Singleton*` 锁、或被异常关机截断的 `Local State` / `Preferences` | 当前 `First Run` 在、无 `Singleton*`、`Local State` 15KB 正常 → **此刻不是故障点** | `Initialize-ChromeProfile` 每次启动前：JSON 解析校验 + 清 `Singleton*` + 补 `First Run`；确认损坏则整个重建（该 profile 只存缓存） |
| 旧实例没退干净导致新实例被"吞" | 见上（1.2 秒重开那条） | 关窗口后等 chrome 进程清零再启动 |

### 4. 显卡 / 显示

| 问题 | 证据 | 结论 |
|---|---|---|
| GPU 进程崩溃 / 驱动 TDR | 近 3 天 `System` 日志**无 4101/4102**，`Application` 日志**无 chrome.exe 崩溃**，Crashpad 无转储 | "驱动崩了"目前**没有证据**，不作为主因 |
| 冷启动时合成层没上屏（窗口是黑的但进程活着） | 现象特征吻合（有窗口、无崩溃、重启首次必现） | 保留两条针对性措施：①判黑屏前先强制重绘（置顶闪一下 + `InvalidateRect`）；②仍黑则用 `--disable-gpu-compositing`（软件合成）重开一轮 |
| 窗口被置顶挂件（NVIDIA Overlay / 桌宠）压住 | 桌面存在 `NVIDIA GeForce Overlay`、`电工猴`（桌宠）等窗口 | 判定改为 9 宫格采样，≥5 格被盖才算"遮挡"；遮挡时返回 `OCCLUDED`，**不判黑屏、不杀进程** |

> 曾经把"黑屏"归因到页面 CSS（全屏 `filter:blur`、`background-attachment:fixed`），那些已经删掉了，`tools/lint_portal.py` 会持续拦截，不用再回头看。

## 三、已经改掉的东西（代码级）

1. **`launcher.ps1` 重写**：单实例互斥 → 快速端口探测（只看 8770）→ 起服务 → 用 `-PassThru` 拿进程号 → 用 `EnumWindows` 按 PID 等窗口（不再信 .NET 的 `MainWindowHandle`）→ 等页面标题就绪 → 强制置前 → 前台且无遮挡时才采像素 → 连续两次黑才降级软件合成重开 → 失败存诊断包 → Edge/默认浏览器兜底。
2. **`tools/grab_screen.py` 增强**：新增 `--wait-window`（按 PID 等窗口）、`--wait-title`（等页面标题）、`--focus`（置前 + 强制重绘）、`--check --hwnd`（前台 + 9 宫格遮挡判定，返回 `OK/BLACK/OCCLUDED/NOWINDOW`）。
3. **`tools/lint_portal.py` 新增硬规则**：必须有互斥、必须按句柄判、必须等页面标题、必须 profile 自愈、必须存诊断包、临时文件必须唯一命名；并禁止裸 `--disable-gpu`（会让 Chrome 启动即退出）、禁止 `| Remove-Item -Force`、禁止固定临时文件名。
4. **`tools/verify_launcher.py` 新增**：自动构造"刚重启"条件并做 9 项可判定断言。
5. **诊断包**：任何失败分支都会写 `docs/diag/<时间戳>/`（窗口清单、chrome 进程号、代理与环境变量、启动日志、应用窗口截图）。

## 四、你自己怎么排查（按顺序，30 秒一轮）

**① 看日志，先分类**（这一步就能定位到上面表格的哪一行）

```powershell
Get-Content "C:\Users\29145\Documents\Codex\2026-10-22\pdf-https-thread-01a15f78-0003-72e3\outputs\portal_launcher.log" -Tail 20
```

对照第一节的表格：没有 `门户已就绪` → 服务问题；`页面加载=False` → 服务/代理；`像素判定：BLACK` → 渲染；`FOCUSED 0` → 被遮挡。

**② 确认服务与页面本身是好的**

```powershell
Invoke-WebRequest http://127.0.0.1:8770/api/health -UseBasicParsing | Select-Object -ExpandProperty Content
```

应返回 `{"ok":true,"portal":"workbench",...}`。若返回别的服务内容，说明端口被占用（启动器会自动换端口，日志里能看到）。

**③ 服务好但页面打不开 → 查代理**

```powershell
Get-ItemProperty 'HKCU:\Software\Microsoft\Windows\CurrentVersion\Internet Settings' | Select-Object ProxyEnable,ProxyServer,ProxyOverride
```

`ProxyOverride` 里应包含 `127.*`。若 FlClash 刚开机还没起内核，先关掉系统代理再双击（启动器已加 `--no-proxy-server`，正常情况下这一步不需要）。

**④ 窗口在但你看不到 → 查是不是被盖住**（开机自启程序抢前台）

```powershell
Get-Process | Where-Object { $_.MainWindowTitle } | Select-Object Id,MainWindowTitle | Format-Table -AutoSize
```

如果列表里有工作台窗口却看不见，说明它在别的窗口下面——重启后手动按 `Alt+Tab` 能找到；新版启动器会把它强制置前。

**⑤ 真黑屏 → 查显卡/驱动**

```powershell
Get-WinEvent -FilterHashtable @{LogName='System'; StartTime=(Get-Date).AddDays(-1)} |
  Where-Object { $_.Id -in 4101,4102 } | Select-Object TimeCreated,Id,ProviderName
```

有 `4101`（显示驱动停止响应）才需要动驱动；没有就说明不是 GPU 崩溃，走软件合成降级那条（启动器第二轮自动加 `--disable-gpu-compositing`）。

**⑥ 想手动重置状态**（清缓存线）

```powershell
Get-Process chrome -ErrorAction SilentlyContinue | Stop-Process -Force
Remove-Item "$env:LOCALAPPDATA\DianGongHouWorkbench" -Recurse -Force -ErrorAction SilentlyContinue
Remove-Item "$env:TEMP\wb_probe_*.txt","$env:TEMP\wb_pixel_check.txt" -Force -ErrorAction SilentlyContinue
```

（该目录只存应用窗口的 Chrome 缓存，删掉不会丢任何数据。）

## 五、怎么验证已经解决

一条命令，自动构造"刚重启"条件并做断言：

```powershell
cd "C:\Users\29145\Documents\Codex\2026-10-22\pdf-https-thread-01a15f78-0003-72e3\outputs"
python tools\verify_launcher.py
```

它会：清掉 profile / 杀干净 chrome / 删掉探测残留 / 清空日志 → 真跑 `launcher.ps1` → 断言 9 项：

1. 启动器退出码 0
2. 日志出现 `页面加载=True`（页面真的加载了）
3. 日志不出现 `页面加载=False`
4. 日志有明确的渲染结论（`渲染正常` 或 `像素无法判定`）
5. 窗口工具正常返回
6. 屏幕上确实存在标题含「工作台」的可见窗口
7. 该窗口前台像素判定为 `OK`（不是 `BLACK`）
8. **反证**：用一个置顶全屏黑窗口盖住它，判定必须是 `OCCLUDED` 而不是 `BLACK`
9. 汇总 9/9

最近一次结果：**9/9 通过**，`像素判定=OK 5%`、遮挡反证 `OCCLUDED`。

**人工验收（最贴近真实场景）**：重启电脑 → 登录后立刻双击桌面「电工猴的此思妙想工作台」→ 应满足：

- 2 秒内出现无地址栏的应用窗口（日志有 `渲染正常，启动成功`）
- 窗口在最前面，不是被盖在别人后面
- 反复双击不会互相打断（第二次会在日志里写"另一个启动器正在运行"并退出）
- 若仍失败：`docs\diag\<时间戳>\` 里有截图和现场信息

## 七、"不黑屏了，但要等很久"怎么定位

这类问题**不看截图、只看日志时间戳**。日志每行都有 `[+x.xxs]`，相邻两行的差值就是该阶段耗时：

```powershell
cd "C:\Users\29145\Documents\Codex\2026-10-22\pdf-https-thread-01a15f78-0003-72e3\outputs"
Get-Content portal_launcher.log -Encoding UTF8 | Select-Object -Last 15
```

或者直接让脚本按阶段拆好：

```powershell
python tools\profile_startup.py --runs 3    # 热启动（平时双击的情况）
python tools\profile_startup.py --cold      # 冷启动（删掉 profile，等价于刚重启）
```

**看哪个数字**：`阶段合计` 明显小于 `总耗时`，说明时间花在日志覆盖不到的环节（启动器自身启动、
端口探测、服务等待）。当年就是这个特征：总耗时 7.57s、阶段合计只有 1.60s，差的 6 秒全在
"21 个端口逐个盲等 + 等 HTTP 200 + 串行启动浏览器"上。

**优化后基线**（2026-10，i7 游戏本）：热启动中位数 **2.66s**，冷启动 **1.66s**，
其中"点击 → 窗口可见"约 0.7s、"点击 → 页面可用"约 1.2s，剩下的 ~1.0s 是像素自检
（在窗口已经可用之后才跑，属于安全开销，不影响手感）。

**如果又变慢了**，按可能性从高到低查：

| 可能 | 怎么确认 | 处理 |
|---|---|---|
| 端口被别的程序占了（走 8771 起的慢路径） | 日志出现 `8770 被别的程序占用` | 找出占用者：`netstat -ano \| findstr :8770` |
| 没复用已在运行的门户 | 日志出现 `已拉起门户服务` 而不是 `复用已在运行的门户` | 正常现象（每次冷启都会拉起一次），除非反复出现在一次启动里 |
| 窗口工具异常、启动器白等超时 | 日志出现 `窗口工具没有返回结果` 或 `像素判定：TOOLFAIL` | 跑 `python tools\lint_portal.py`，它对每个子命令做冒烟测试 |
| Chrome profile 损坏、回退重建 | 日志出现 `profile 已重建` | 单次可接受；连续出现说明 profile 写入有问题 |
| 杀毒软件/开机自启抢占磁盘 | 开机后第一次特别慢、之后正常 | 把 outputs 目录加入杀软白名单 |
| 环境变量缓存失效 | 每次启动都要重新扫 PATH | 删掉 `%LOCALAPPDATA%\DianGongHouWorkbench\env.json`，下次会自动重建（只会慢一次） |
